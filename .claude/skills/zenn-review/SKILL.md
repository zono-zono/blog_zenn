# Zenn 記事の添削

`articles/` と `books/` にある Zenn 記事を、公開前に添削するためのスキル。
**指摘して修正案を出すところまでが既定の動き**。本文の書き換えは、ユーザーが「直して」と頼んだときだけ行う。

## 手順

### 1. 対象を決める
- ファイルが指定されていればそれを使う。
- 指定がなければ `git status --short articles books` を見て、変更中の記事を対象にする。複数あれば一覧を出して聞く。
- frontmatter（`title` / `emoji` / `type` / `topics` / `published`）も確認する。`published: true` なら公開前の最終チェックとして厳しめに見る。

### 2. textlint を実行する（機械チェック）
```bash
npx textlint -f compact <file>
```
- textlint MCP サーバー（`.mcp.json` の `textlint`）が使えるなら、そちらを使ってもよい。
- `prh`（表記ゆれ）の指摘は、ほぼそのまま採用してよい。
- `sentence-length` / `no-doubled-joshi` / `preset-ai-writing` は、文脈を見て採否を判断する。無理に守ると不自然になる場合は、そう書いて見送る。
- コードブロック・インラインコード・URL 内の指摘は無視する（設定上は出ないはずだが、出た場合）。

### 3. 読んで添削する（textlint では拾えない部分）
次の4観点で本文を読む。詳細なチェック項目と言い換え例は references を参照する。

| 観点 | 参照 |
|---|---|
| A. 炎上・トラブルのリスク | [references/risk-checklist.md](references/risk-checklist.md) |
| B. 日本語として自然か、エンジニアらしい言い回しか | [references/style-guide.md](references/style-guide.md) |
| C. Databricks まわりの技術的な正確さ | [references/databricks-terms.md](references/databricks-terms.md) |
| D. 記事構成（Zenn の技術記事として読みやすいか） | 下の「構成チェック」 |

**A は必ず全項目を確認する。** B〜D は、記事の内容に合うものだけでよい。

#### 構成チェック（D）
- 冒頭で「この記事で何がわかるか」「対象読者」「前提（環境・バージョン・検証日）」が分かるか。
- 試行錯誤の記事なら「やりたかったこと → 詰まったこと → 原因 → 解決策 → 学び」の流れになっているか。
- 見出しだけを読んでも話の流れが追えるか。
- 最後にまとめと参考文献（公式ドキュメントへのリンク）があるか。
- Zenn 記法（`:::message`, `:::details`, `@[card](url)`）を適切に使えているか。

### 4. 結果を報告する
重大度の高い順に、次の形式でまとめる。**言い換え案は必ず具体的な文で出す**（「もう少し柔らかく」のような抽象的な指摘だけで終わらせない）。

```
## 添削結果: <記事タイトル>

### 🔴 公開前に必ず直す（炎上・機密・事実誤り）
- L12「〜〜」
  - 理由: …
  - 修正案: 「〜〜」

### 🟡 直したほうがよい（不自然な表現・誤解を招く書き方）
- …

### 🟢 好みで（読みやすさの改善）
- …

### textlint
- エラー N 件（うち自動修正可 M 件）。採用 / 見送りの判断を一言添える。

### 総評
- 2〜3行。良い点も1つは挙げる。
```

- 該当がない区分は「なし」と書く（空欄にしない）。
- 行番号は実ファイルの行番号を使う。

### 5. 修正する（頼まれた場合のみ）
- `prh` などの自動修正できる指摘は `npx textlint --fix <file>` でまとめて直し、差分を見せる。
- 文章の言い換えは Edit で1箇所ずつ行う。筆者の口調（ですます調、一人称、くだけ具合）は変えない。
- 修正後にもう一度 `npx textlint <file>` を実行し、結果を報告する。

## やらないこと
- 記事の主張や結論そのものを書き換えない。技術的に誤っている場合は、指摘して根拠（公式ドキュメントの URL）を示すにとどめる。
- 筆者の体験談を一般論に書き換えない。「私の環境では」という一次情報は技術ブログの価値なので残す。
- AI っぽい無難な文章に均さない。言い回しの癖は、誤解や炎上につながらない限り残す。
