# 日本語・エンジニアらしい言い回しのガイド

目標は「日本のエンジニアが書いた、読みやすい技術ブログ」。
教科書のような硬さも、AI が書いたような均一さも避ける。**筆者の口調は尊重する。**

## 1. 翻訳調・AI 調を自然にする

| 不自然 | 自然な言い換え |
|---|---|
| 〜することが可能です | 〜できます |
| 〜を行います（「設定を行う」「実行を行う」） | 設定します / 実行します |
| 〜することができます | 〜できます |
| 〜という形になります | 〜になります |
| 〜において | 〜で |
| 〜に関して | 〜について（または削る） |
| 非常に重要です / 極めて強力です | 重要です / 便利です（強調は本当に必要なときだけ） |
| 〜を活用することで、〜を実現できます | 〜を使うと、〜できます |
| シームレスに / 包括的な / 革新的な | 具体的に何がどう良いのかを書く |
| 結論から言うと：（英語式コロン） | 結論から言うと、 |
| 〜しましょう！（連発） | 1記事に1〜2回まで |

## 2. 技術ブログでよく使う自然な言い回し
試行錯誤系の記事では、次のような表現が自然に馴染む。無理に使う必要はないが、硬すぎる文の言い換え候補にする。

- 状況: 「〜でハマりました」「〜で詰まりました」「〜で地味に困ったのが〜」「〜が刺さりました」
- 試行: 「〜を試してみました」「〜で検証しました」「ざっくり言うと」「雑に言うと」
- 解決: 「〜で解決しました」「〜で回避できました」「〜するのが手っ取り早いです」
- 所感: 「〜なのは嬉しいポイントです」「〜は少し癖があります」「〜は割り切りが必要です」
- 留保: 「私の環境では」「今回の要件では」「2026年10月時点では」

**使いすぎ注意**: 「ハマった」「爆速」「神」「最強」のようなくだけた語は、1記事に数回までにする。

## 3. 弱い表現・推量の扱い
- 「〜と思います」「〜かもしれません」は、**事実を書く箇所では削る**（「Delta Lake はトランザクションをサポートしていると思います」→ 確認して断定する）。
- **意見・所感・未検証の箇所では残す**（断定すると炎上リスクが上がる）。
- 1段落に3回以上続く場合だけ、まとめて減らす提案をする。

## 4. 文の組み立て
- 1文1メッセージ。読点が4つ以上あったり、100字を超えたりする文は分割を提案する。
- 主語を省きすぎて「誰が / 何が」が分からない文を直す（特に「〜したところ、〜になった」の連鎖）。
- 「〜が、〜が」と逆接が続く文は分ける。
- 指示語（これ / それ / この設定）が何を指すか曖昧なら、名詞に置き換える。

## 5. 表記
textlint（prh）で拾えない部分を見る。
- 半角英数字と全角文字の間のスペースは、**記事内で統一されていれば**どちらでもよい（混在だけ指摘する）。
- 製品名・機能名は公式表記に合わせる（[databricks-terms.md](databricks-terms.md)）。
- コード上の識別子（テーブル名・関数名・設定キー）はインラインコード（`` ` ``）で囲む。
- 長音: -er/-or/-ar の語は「ー」を付ける（サーバー、ユーザー、コンテナー）。-ry/-ty/-gy の語は付けない（ライブラリ、クエリ、メモリ、セキュリティ）。ただし Databricks 日本語ドキュメントの表記が別ならそちらに従う（例: 「クラスター」）。

## 6. 見出し
- 「〜について」「〜の説明」のような空の見出しを、内容が分かる見出しに直す（「Auto Loader のスキーマ進化で詰まった点」）。
- 見出しの末尾に句点を付けない。
